# EarthTrend Explorer

A web application for exploring long-term change in Earth-science time series: estimate a trend, see how
uncertain it is, compare regions, and read a plain-language explanation that is generated by fixed rules from
the computed statistics.

> **Data status: observed global data and synthetic regional demo data are loaded as two separate classes.**
>
> * **Observed global data** (`datasets/observed_global/`): NASA GPM IMERG V07 global area-averaged monthly
>   precipitation and random error (mm/hr), 1998-01 to 2025-09, from Giovanni CSV exports. It is a single global
>   average: it supports no regional claim, map pin or comparison.
> * **Synthetic regional demo data** (`datasets/synthetic_regional_demo/`): India, Amazon and Central Africa series made
>   up for software testing and shown as **SYNTHETIC DEMO — NOT NASA OBSERVATIONS** everywhere, including exports.
> * **Real regional analysis is disabled** until genuine regional observations are supplied.
>
> See [docs/DATA_PACKAGE.md](docs/DATA_PACKAGE.md). Everything else the app shows comes from one of two places:
>
> 1. a **synthetic demo dataset** (`backend/data/earth_science_trend_demo.csv`), generated by
>    `backend/scripts/generate_demo_data.py` from a seeded random number generator. It is artificial. It is not
>    NASA data, not satellite data and not an observation of the real Earth system. Every screen, API response and
>    CSV export that uses it says so; or
> 2. a CSV file **you upload yourself**, which is kept separate from the demo data and always labelled
>    *unverified*.
>
> Nothing in this repository has been scientifically validated against any NASA product. See
> [docs/NASA_DATA_INTEGRATION.md](docs/NASA_DATA_INTEGRATION.md) for what is needed to connect the real dataset.

## What it does

| Page | Purpose |
| --- | --- |
| **What happened?** (home) | Pick a region and a month range, read an evidence-tagged text summary built only from the dataset (what the numbers were, how they differ from the usual value for that calendar month, unusual months, and an honest "why" that never names a cause the data cannot support), then step or play through the months on a 3D globe. A rule-based chat ("what happened in India from 2010 to 2015?") drives the same page. A Markdown report with the dataset checksum can be downloaded. |
| **Trend Analysis** | One variable in one region: direction, slope per year with a confidence interval, p-value, Mann-Kendall, Sen's slope, autocorrelation and seasonality diagnostics, a chart with fitted lines, and a traceable explanation. |
| **Upload Dataset** | CSV profiling, explicit column mapping, a data-quality report, confirmation of ambiguous choices, then import. |
| **Methodology / About** | The methods, their assumptions, default parameters and references. |

Design rules the app follows throughout:

- **No invented data.** Missing values stay missing (never zero, never interpolated). Units, regions, coordinates,
  missions and instruments are shown only if they exist in the file. If a file has no latitude/longitude the map
  is replaced by an explanation.
- **Honest statistics.** The headline test is chosen from the data's own diagnostics. If autocorrelation cannot be
  corrected for, the result is labelled *exploratory (uncorrected)* instead of being presented as standard.
  A non-significant result is never described as proof that there is no trend, and no result is described as a cause.
- **Deterministic explanations.** The interpretation text is produced by rules in
  `backend/app/services/explain.py`. No Groq, OpenAI, Gemini or other AI service is called or required, and
  every sentence lists the numbers it was built from.
- **Provenance travels with the data.** Every API response carries a `provenance` block; every CSV export carries
  `data_source` and `is_synthetic`.

## Architecture

```
Browser (Next.js 16 App Router, React 19, TypeScript, Tailwind 4, Recharts)
   |   renders results; never recomputes statistics
   |   HTTP/JSON  (NEXT_PUBLIC_API_URL, default http://127.0.0.1:8000)
   v
FastAPI backend (Python 3.11, pydantic, pandas, NumPy, SciPy, statsmodels, pymannkendall)
   |-- routers/        datasets, ingest (profile/upload), analysis (analyze/compare/explain/methodology)
   |-- services/ingestion/   DatasetAdapter interface + CSV adapter + format registry
   |-- services/stats/       trend, diagnostics, sampling (pure functions)
   |-- services/analysis.py  orchestration; explain.py rule-based text; store.py in-memory dataset store
   `-- data/           demo CSV (read-only) and uploads/ (persisted uploads)
```

All data, whatever its source, is normalised to one canonical long-format schema before analysis
([docs/DATA_SCHEMA.md](docs/DATA_SCHEMA.md)). A new data format only needs a new adapter.

## Install

From the repository root.

**Backend**

```bash
cd backend
python -m venv .venv
```

Activate the environment, then install:

```bash
# Windows PowerShell:   .venv\Scripts\Activate.ps1
# Windows Git Bash:     source .venv/Scripts/activate
# macOS / Linux:        source .venv/bin/activate
pip install -r requirements.txt
```

**Frontend**

```bash
cd frontend
npm install
```

## Configure (optional)

Defaults work without any configuration. Templates are provided if you want to change something:

- `backend/.env.example` -> `backend/.env` (CORS origins, upload limits). All variables use the `EARTHTREND_` prefix.
- `frontend/.env.example` -> `frontend/.env.local` (`NEXT_PUBLIC_API_URL=http://127.0.0.1:8000`).

No API keys are needed. `NEXT_PUBLIC_` variables are visible in the browser, so never put secrets in them.

## Run

Open two terminals.

**Terminal 1: API** (from `backend/`, with the virtual environment active)

```bash
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

**One command instead of two terminals** (from the repository root): `python scripts/dev.py` starts both servers from
this checkout. It refuses to start if port 8000 or 5174 is already taken and never kills anything. This matters on
Windows, where an old server bound to `0.0.0.0:8000` can coexist with a new one on `127.0.0.1:8000` and silently
answer with outdated code (symptom: `/api/health` reports `datasets_loaded: 1` and `/api/diagnostics` returns 404).
To find an old server: `netstat -ano | findstr ":8000 "`, then stop it yourself.

**Terminal 2: web app** (from `frontend/`)

```bash
npm run dev
```

For a production build instead of the dev server:

```bash
npm run build
npm run start
```

| What | URL |
| --- | --- |
| Web app | http://localhost:5174 |
| API health check | http://127.0.0.1:8000/api/health |
| Interactive API docs (Swagger UI) | http://127.0.0.1:8000/docs |

The API must be running for the web app to show data; if it is not, the app shows a clear

## Using the demo data

The backend loads `backend/data/earth_science_trend_demo.csv` on start-up (2,520 rows: 3 synthetic indices,
4 regions, monthly 2000-2023, with deliberate gaps, opposite trends, seasonality and mixed sampling so that every
feature and warning can be exercised). It is read-only and cannot be deleted through the API. To regenerate it:

```bash
cd backend
python scripts/generate_demo_data.py
```

## Uploading your own CSV

1. Open **Upload Dataset** and choose a `.csv` file (up to 25 MB). Other formats are rejected with an explanation:
   NetCDF, HDF and GeoTIFF are not supported yet.
2. Review the preview and the **suggested** column mapping. Column names are only ever suggested, never assumed.
3. Anything the file does not contain must be **declared by you**: the unit, the data source, and whether the data
   are synthetic/test data or not. The app does not guess units or provenance, and never converts units.
4. Choose **Validate file** for a dry-run quality report (invalid dates, invalid values, duplicates, mixed units,
   suspicious sentinel values such as -9999). Confirm any ambiguity it lists.
5. Choose **Import dataset**. It appears in the dataset selector as an *Uploaded dataset*. Uploads are stored in
   `backend/data/uploads/` and survive restarts until you delete them. They are never marked as NASA-verified.

CSV exports from the app neutralise spreadsheet-formula injection (cells starting with `=`, `+`, `-`, `@` are prefixed).

## API overview

All routes are under `/api`. Errors use the shape `{"error": {"code", "message", "details?"}}`.

| Method and path | Purpose |
| --- | --- |
| `GET /api/health` | Liveness, dataset count, whether a NASA dataset is integrated (currently `false`). |
| `GET /api/datasets` | Datasets with status (`observed_global`, `synthetic_regional_demo`, `synthetic_demo`, `uploaded`, `nasa_verified`), their source/scope/coverage/unit/limitations, and any package load problems. |
| `DELETE /api/datasets/{id}` | Delete an uploaded dataset (the demo dataset is refused with 403). |
| `GET /api/metadata?dataset_id=` | Variables, regions, units, series, fields present, spatial availability. |
| `GET /api/observations` | Paginated rows; `format=csv` for export with provenance headers. |
| `POST /api/profile` | Inspect a CSV and propose a column mapping. |
| `POST /api/upload` | Validate (`dry_run=true`) or import a CSV with a mapping. |
| `POST /api/analyze` | Trend analysis of one variable in one region. |
| `POST /api/compare` | Comparison of one variable across regions. |
| `GET /api/diagnostics` | Missingness, month-of-year summary, autocorrelation and random-error diagnostics for one series. |
| `POST /api/explain` | Rule-based explanation for a supplied analysis or comparison. |
| `POST /api/upload-grid` | Import a NetCDF grid (time, lat, lon). Stores the grid and an area-weighted regional series. |
| `GET /api/grid` | Per-cell values and anomalies for one month of a gridded dataset. |
| `GET /api/regions` | Regions in a dataset with variables, coverage and map extent. |
| `POST /api/story` | Evidence-tagged summary of one region and month range (no external AI). |
| `POST /api/chat` | Rule-based chat: parses place, variable and time against the loaded dataset and returns what it understood plus an action for the page. |
| `GET /api/overview` | Whole-record view of one region: year-by-month matrix, usual month, yearly and decade anomalies, records, trend, rule-based sentences with evidence. |
| `GET /api/atlas` | Every region by year on one standardised colour scale. |
| `GET /api/snapshot` | Every region with a known map position for one month or whole year (the "map in motion"). |
| `GET /api/methodology` | Methods, default parameters and references. |

Limits: uploads over 25 MB are rejected with 413 (configurable); filenames are sanitised and server-generated IDs
are used on disk; CORS allows only the local frontend origins by default.

## NASAX Earth Time Machine (home page)

The home page (`/`) is a full-screen CesiumJS 3D globe. Search a place, pick a start and end year, press **Explore**:
the globe turns to the place, drops a marker, flies in, shows the **latest available observation** (never labelled live),
then compares the two ends of your period and reports one of three outcomes:

* **Change detected** - lost / gained water, hotspots with real polygon boundaries, auto-zoom to the biggest one.
* **No clear change** - what was analysed and the measurements, with an option to explore anyway.
* **Insufficient data** - what is missing, which dates exist, and a suggested supported period. This is never reported as "no change".

Map modes: latest, historical (bottom timeline: only dates that exist, draggable, play/pause, speed, prev/next), before/after,
swipe, difference, hotspots. Years outside a dataset's coverage are explained, and a partial overlap is analysed with an explicit notice.

**Data.** The app reads the **India Historical Atlas** in `datasets/india_historical_atlas/processed/` (see the next section). Each dataset is a
folder with `dataset.json` and `observations/*.tif` (Cloud Optimized GeoTIFF). Two kinds exist and are labelled everywhere in the interface:
**Satellite Observations** (derived from official JRC / ESA files that were really downloaded) and **Illustrative Dataset** (generated demonstration
layers, not satellite imagery). A place with no dataset is shown on the globe with **Data Unavailable**; no history is ever invented.
Search covers states, districts, cities, localities, landmarks and natural features with suggestions, voice commands and Back/Forward.

**Method.** Same-season composites at both ends, water-frequency threshold, common-grid alignment, cloud/no-data excluded, feature clean-up,
geodesic per-row pixel areas (hotspot polygons re-measured in UTM), Theil-Sen/Kendall progression, a year-to-year scatter test, configurable
thresholds (`params` on `POST /api/explorer/analysis/detect-change`).

**AI.** Set `GROQ_API_KEY` (env only) to have Groq explain results through backend tools (summary, hotspots, area series, quality). With no key, or on
any failure, a deterministic report from the same numbers is used and the UI says which one you are reading. Neither claims causes.

API: `/api/explorer/` - `locations/{search,suggest}`, `locations/{id}/boundary`, `session`, `datasets`, `datasets/{id}/{metadata,statistics}`, `catalogue`, `source-registry`, `datasets/{id}/observations`, `.../observations/{date}/layer.png`,
`analysis/detect-change`, `analysis/{id}/{change-summary,hotspots,change-layers,layers/{difference.png,before.png,after.png,difference.tif},explain}`, `ai/chat`.

Run: `python scripts/dev.py`, or backend `uvicorn app.main:app --port 8000` plus `npm run dev` in `frontend/` (the `predev` script copies Cesium assets to `public/vendor/cesium`).
The earlier story/trend/upload pages remain under `/story`, `/trend`, `/upload`.

| --- | --- | --- |

Build and check (from the repository root, with the backend virtualenv active):

```bash
python scripts/generate_india_atlas.py --all    # download, generate, process, boundaries, statistics, change detection, manifest, catalogue
python scripts/generate_previews.py             # PNG previews
python scripts/validate_datasets.py             # writes documentation/validation_report.json
python scripts/generate_evidence.py             # NASAX_JUDGE_EVIDENCE/
```

`generate_india_atlas.py` without flags only rebuilds the manifest and catalogue. Each step can run alone (`--steps official,process`). Official downloads
are recorded as `VERIFIED_DOWNLOADED`, `VERIFIED_METADATA_ONLY`, `ACCESS_REQUIRES_AUTHENTICATION` or `NOT_ACCESSED`; nothing is marked downloaded without a checksum.
To add a place: add a `Region` in `backend/app/explorer/atlas.py` (illustrative) or a recipe in `scripts/process_satellite_data.py` (official), then re-run.
Honest limits: no Landsat, Sentinel-2 or Bhuvan scenes were downloaded; the Himalayas region is entirely illustrative; city, locality and landmark outlines are
approximate areas marked as such; Cesium shows no real terrain relief.

## 3D story map

The home page draws the selected region on a MapLibre 3D globe. **Colour** is the difference from the usual value for that
calendar month (blue above, vermillion below) and **column height** is the value. The bundled datasets hold one value per
region per month, so the colour covers the whole region and the outline is labelled as an approximate extent; the map
never implies a per-place pattern. A **NetCDF grid** uploaded on the Upload page (3-D variable with time, latitude, longitude; classic or NetCDF4) gives true per-cell maps: each valid cell is drawn, coloured by its difference from that cell's usual value for the month and raised by its value. Missing cells stay empty, the unit comes from the file ("unspecified" if absent), grids over 100 cells per axis are block-averaged for display only, and the regional statistics are cos-latitude-weighted means over valid cells. GeoTIFF is not supported yet.
The earlier Earth Explorer wizard, 2D atlas, Overview, Regional Comparison and Data Explorer pages were removed; the
`/api/compare` endpoint and the geography endpoints remain available.

## Whole-record view (the chronicle)

Above the period summary the home page shows the whole record for the chosen region: **yearly stripes** (one per year,
coloured by the mean standardised anomaly), a **rain calendar** (every month as one cell), the **yearly rhythm** (usual
month with its spread, the most above- and below-normal years drawn over it), decade bars, record lists, a
rule-based "story in plain words" with evidence on hover, an **all-regions heatmap** (every region by year; click a row to
open it) and **the map in motion**: one 3D tile per region with a year slider and play button. Clicking a stripe or
calendar cell sets the period for the summary and the map below.

Honesty rules: months with no value stay empty; a year with fewer than 10 valid months gets no yearly number; usual values
need at least 3 observations per calendar month; the straight-line change is descriptive and says nothing about cause;
colours are standardised anomalies, so regions are comparable but raw amounts are not. Tiles on the map sit at the approximate
centre of each region from a built-in reference table (currently the 36 India Meteorological Department rainfall
subdivisions); they are not boundaries and are labelled as approximate. Regions without a known position are listed, never drawn.

**Wide CSVs** (one row per region and year, one column per month) are not read directly. Convert them with
`python -I scripts/wide_rainfall_to_long.py in.csv out.csv [unit]`, which drops blank cells instead of filling them.

## Known limitations

- **No real NASA data.** Only synthetic demo data and user-uploaded CSVs are supported. NetCDF, HDF, GeoTIFF and
  Zarr are not read, and nothing here pretends otherwise.
- **Long-format CSV only.** One row per observation (`date, region, variable, value, ...`). Wide-format files
  (one column per region or variable) must be reshaped first.
- **Seasonal Mann-Kendall treats seasons as independent** (the covariance-adjusted version is not implemented), so
  seasonal series with autocorrelation are reported as *exploratory (uncorrected)*. The Hamed-Rao correction is used
  only for gap-free, regular, non-seasonal series; annual aggregation is the usual route to it.
- **Sen's slope is limited to 4,000 observations per series** (it stores all pairwise slopes); longer series should be
  aggregated to quarterly or annual values. Mann-Kendall is limited to 20,000.
- **No spatial analysis.** Regions are labels. Region names are never converted to coordinates or boundaries. The story map colours whole regions only; the extents used to place the camera for demo region names are approximate display values, not dataset values.
- **Datasets live in memory**, loaded at start-up; uploads are persisted to disk. This is a single-user local tool,
  not a multi-user service: there is no authentication and it has not been security-hardened for public hosting.
- **The selected dataset is not remembered** across a browser reload.
- **Accessibility** has been designed for (labels, focus states, keyboard navigation, data tables behind charts,
  non-colour cues) and spot-checked, but not audited with a screen reader or against WCAG in full.
- **Statistical caveat:** none of the methods has been validated against a real Earth-science product. Treat all output
  as a demonstration of the method until the real dataset has been integrated and reviewed by a domain expert.

## Troubleshooting

- **`Cannot reach the EarthTrend API`** - start the backend (see *Run*), or check `NEXT_PUBLIC_API_URL`.
  If you changed the frontend origin, add it to `EARTHTREND_CORS_ORIGINS`.
- **`address already in use`** - another process holds port 8000 or 5174. Stop it, or start on another port
  (`--port 8001` for the API / `npm run dev -- --port 3000` for the web app) and update
  `NEXT_PUBLIC_API_URL` and the CORS origins to match.
- **Vitest fails with `Cannot find native binding`** - an npm optional-dependency bug
  ([npm/cli#4828](https://github.com/npm/cli/issues/4828)). Install your platform's binding without saving it, using
  the version printed by `npm ls rolldown`, for example on 64-bit Windows:
  `npm install --no-save @rolldown/binding-win32-x64-msvc@<rolldown version>`; or delete `node_modules` and
  `package-lock.json` and run `npm install` again.
- **`Next.js ignored package-lock.json in <home folder>`** - harmless; `next.config.ts` pins the workspace root.
